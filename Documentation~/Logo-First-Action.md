# Your first viewer action: show the Muxy logo

This example flashes a logo in your game for five seconds when a viewer activates an action. Start with a free test action. A visible logo confirms receipt without modifying gameplay; connecting alone does not confirm that an action reached the game.

1. Install the package and put one `MuxyGatewayManager` and one connection UI in the scene. Configure the manager's Game ID to match **Linked Games** in the broadcaster's Twitch extension configuration. Set up an EventSystem compatible with your project's input system.
2. On the manager, add a Game Action with ID `show-muxy-logo`, name `Show Muxy Logo`, category **Neutral**, state **Available**, impact 1, and count 65535. Configure the matching action in the extension and make it free for this test. Leave its individual callback empty: the sample listens to the manager's `OnAnyGameActionUsed` event.
3. Create a Canvas with a UI Raw Image child called `Logo`. Assign the package's `Muxy_Logo_Solid_White` image to its Texture field, then choose its position and size. Make sure the Canvas and its parents are active. Keep the logo object separate from the script object; the script hides it until an action arrives.
4. In Unity Package Manager, select Muxy Hypeline, expand **Samples**, and import **First viewer action**. Alternatively, copy [HypelineLogoDemo.cs](examples/HypelineLogoDemo.cs) into your project's `Assets` folder. Attach it to an active scene object. Assign the scene's manager and the `Logo` object to its Inspector fields. Save the scene.
5. Run the game, connect with a fresh PIN, and activate **Show Muxy Logo** from a separate viewer session in the extension. The logo should appear for five seconds, and the sample requests acceptance of the action. If the logo is unavailable, it requests a refund instead.

`ShowLogo()` can also be wired to a local UI button to preview the visual. A local preview does not test Twitch, a transaction, or a refund. The sample suppresses duplicate transaction IDs only for its current component lifetime. It does not persist a transaction ledger across restarts, verify server acknowledgement, or provide exactly-once delivery. Production games should use a durable transaction ledger and reconcile uncertain outcomes with the service; do not claim an action was refunded or accepted until that outcome is confirmed by the integration's contract.

Never send PINs, authentication tokens, or unredacted transaction details in support logs. If a live action does not arrive, verify the broadcaster channel, connection state, exact action ID, action availability, and extension setup.
